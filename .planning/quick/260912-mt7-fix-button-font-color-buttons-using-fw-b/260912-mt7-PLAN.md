<diagnosis>
Root cause is a CSS specificity collision inside `app/family-world.css`:

| Line | Selector | Specificity | Sets |
|------|----------|-------------|------|
| 87 | `.family-world a` | (0,1,1) | `color: var(--color-accent)` — #ec3013 red |
| 88 | `.family-world a:hover` | (0,2,1) | `color: var(--color-accent-600)` — #dd2b0f red |
| 127 | `.fw-btn-primary` | (0,1,0) | `background: var(--color-accent)` + `color: var(--color-bg)` |

`.family-world a` (0,1,1) outranks `.fw-btn-primary` (0,1,0) on the class-count tiebreak, so
anchor-rendered primary buttons get red text on the red `--color-accent` background.

Two facts verified against the codebase that constrain the fix:

1. **Only the anchor-rendered primaries are broken.** Of the 10 `fw-btn fw-btn-primary`
   usages, `app/page.tsx:43`, `app/explore-grandmas-world/page.tsx:155`,
   `app/components/FamilyGallery.tsx:264` and `:550` are `<a>` (broken);
   `app/components/AddFamily.tsx:554,571,731` and `app/components/LiveWorld.tsx:308,395,440`
   are `<button>` (already correct, near-white text). The fix makes `<a>` match `<button>`.

2. **A two-class fix is NOT enough.** `.family-world .fw-btn-primary` is (0,2,0), which fixes
   the rest state but *loses to line 88's* `.family-world a:hover` (0,2,1) — the text would go
   invisible again on hover. The fix must reach (0,3,0) or higher. `.family-world
   .fw-btn.fw-btn-primary` is (0,3,0) and beats both line 87 and line 88 in one rule, and
   every usage applies `fw-btn` and `fw-btn-primary` together (verified across all 10 sites),
   so it matches every instance.

Out of scope, deliberately: `.fw-btn-ghost` (line 133) already sets `color: var(--color-accent)`
on purpose — the link rule overrides it with the same value, so nothing visibly breaks.
`.fw-btn-secondary` (line 130) sets no color and sits on a transparent/light background, so
accent-colored text there is readable. Per the literal ask, scope the fix to primary only.
</diagnosis>
